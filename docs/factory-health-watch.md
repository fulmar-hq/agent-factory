# Independent factory alarm

The deterministic evaluator is #148 part one. This runtime supplies #150's independent read-only controller/native/tick/disk collectors, durable separate health SQLite, and existing Alido Mail bridge. It has no model or AWS call and does not open credential files. Missing evidence remains actionable unknown; neither an owner wake nor a queued outbox row proves a renewal or delivery.

The same independent five-minute job also checks the idle queue. A successful queue observation at most five minutes old, zero runnable tickets, positively stopped builder custody, an unpaused factory and fresh native usage allowing high-benefit work are required. After more than twenty minutes without actual builder start/exit/cleanup activity it inserts one stable **action** mail to Coordinator. Owner turns and maintenance reviews cannot conceal the stall. The observer reads controller state read-only (its only controller writes are to queue a repeat's intake wake and to withdraw one that has not started, both described below) and keeps observations/incidents in `health/idle-queue.sqlite`. Unknown queue/usage/custody stays visibly ineligible, never healthy proof. If queue/complete inventory evidence remains unavailable for more than twenty minutes, a separate persistent observation-gap episode sends one action to Coordinator, explicitly reporting unknown evidence rather than claiming the queue is empty. A positive paused or nonempty reading ends that observation-gap episode; pending delivery still reconciles after recovery. A bridge insert is queued only; read back `wake_state=woken` and its actual wake ID before claiming Coordinator was woken. Preserve all observations and mail. Later actual builder activity rearms a new episode.

## Idle alarm: repeats, limits and duration

In plain words: the first idle alarm used to be the only one, and a paused factory was never timed. Now an empty queue is raised again on a fixed, bounded schedule, an idle caused by a limit is named and timed without touching the limit, and any idle of two hours is one plain line to Vincent. All of it lives in `launcher/idle-queue.ts`; the fixed numbers are `IDLE_RULES` in that file.

**Repeats.** While the first alarm's own conditions still hold (queue freshly confirmed empty, builders stopped, not paused, usage allowed), the alarm repeats 60 minutes after the first alarm and then every 2 hours after the previous repeat, at most 12 times in any 24 hours across all episodes. A repeat sends no mail. It queues one `product-intake` owner wake, the existing kind, so the tick dispatches it and applies its `intake.json` exactly as it does any other intake. The wake adds `idleRepeat`: how long the queue has been empty and how the last intake ended (returned no tasks, result refused by the launcher and why, did not finish). A repeat that falls due while the conditions do not hold is not caught up later; the next one fires at the first eligible reading. If the controller is busy the step is not recorded and the next run tries again. Each repeat's record in `records` (kind `repeat`) is later filled in with when its wake was dispatched, how it ended and the ready count afterwards.

The repeat's wake keeps the supply loop's rule of one intake at a time, from this file's side:

- It is never queued while the ordinary round's wake (`intake-round`) or an earlier repeat's wake is queued, starting or running. The watcher asks again at each run (`repeatWaiting` in the job's output) and queues the wake once that intake has finished. If the other intake is still in flight 30 minutes after the repeat fell due, the step is recorded with that reason and no wake, and the schedule moves on.
- A wake that has not started is withdrawn at the next run (state `expired`, as the supply loop marks its own, plus one `idle-repeat-wake-withdrawn` event with the reason) when the idle it was queued for no longer holds (paused, usage stop, ready work, a builder ran, or the queue can no longer be read), when an ordinary intake wake has been queued beside it, or when it has not been dispatched within 30 minutes. A wake the tick has already claimed is left alone. The reason is kept on the repeat's record as `withdrawn`.
- It copies the newest ordinary intake's view of the backlog only when that intake finished under two hours ago, its result has been applied, and neither it nor the previous repeat proposed a task. Otherwise no view is attached and the wake tells the owner to read the current open issues first.

What this cannot close from here: the tick dispatches a queued wake without asking the watcher, so a wake queued at one health run can still start during the up to five minutes before the next run would withdraw it; and the supply loop does not know about a repeat's wake, so it can start its own round while a repeat is running. Both need a change in the supply loop or the tick, which this file does not make.

**Idle explained by a limit.** When nothing is being built because of a limit, there is no repeat and no intake wake. The watcher writes one `idle-by-limit` record per limit episode that says `idle by limit`, names the limit, its start or end where known and, for a pause, who set it when the pause event recorded that. The limits it recognises are a pause; a usage stop, with its reset time (found when the queue is empty, or when every ready ticket was refused for it); and ready work with no claim this tick where every refusal was `worker unqualified`, `disk admission refused`, `usage window missing` or `wallet empty`. A refusal that is not a limit, or a claim, means it is not a limit's idle. So does any builder that is not positively stopped: "nothing running" is decided on the same proof as the empty-queue alarm (every builder at rest, no process, cleanup verified), never on status alone. A stale or unknown usage reading is missing evidence, not a limit. The install freeze is not on this list because it never stops builders. Nothing in this path resumes, lifts, shortens or works round a limit, and it changes no gate, capacity, wallet or schedule.

**Duration is watched whatever the cause.**

- A pause with ready work and no running builder for 30 minutes (the contract's expected duration for a pause) queues one action mail to Platform that asks only "is this pause still intended?". Its id is `pausedWithReadyActionId(pause start)`, built from the loop contract's `roleActionId`. Any other producer of the same question must build the same id so the mail store keeps one row; the watcher accepts a row another writer already raised under that id and adds no second one.
- Any idle that reaches 2 hours queues one routine line for Vincent naming the cause, for example `Idle 2 h: paused since 15:16 with 31 ready.`, `Idle 2 h: usage stop until Friday 03:00.` or `Idle 2 h: queue empty, intake returned no tasks.`. Its id is the contract's `loop:routine:idle:<cause>:<Toronto day>`, so there is one a day per cause: a second line the same day only when the cause changes.
- An idle that is neither a confirmed empty queue nor a confirmed limit is timed too, as long as no builder may be running (no session reserved, starting or running, and no live process): ready work nothing claims for a reason that is not a limit, queue or issue evidence that cannot be read, a stale or unknown usage reading, or builders whose stop is not proven. Its line says what is known, for example `Idle 2 h: 3 ready and none claimed: repository workspace not configured.` or `Idle 2 h: queue reading unavailable.`, under the one cause `not-explained`. It waits 30 minutes past the two-hour mark so that one unreadable run does not take the line from a cause the next run can name. It never queues a repeat or an intake wake.
- The watcher bounds the line itself, whatever a mail gate later does. At most 2 idle lines are written in any 24 hours across all causes. A `not-explained` line is never a second line. For an idle no limit explains, no line is written while the launcher's own "nothing claimable for 2 hours" line (`supply-idle-alert`, from `launcher/supply-idle.ts`) was queued in the last 24 hours. A line that was due and held is written to `records` as `idle-line-held` with the reason and returned as `lineHeld`.

Today nothing between this row and Telegram holds it: Alido Mail sends a pending row for Vincent at once, at any hour. The daily budget for messages to Vincent, which tiers this row by its `loop:routine:` id, is a separate change in the mail checkout; until it is installed the bounds above are the only ones. If the watcher's line is written before the launcher's own two-hour line, the launcher's line still follows it; removing that second writer is a change to `launcher/supply-idle.ts`.

Idle time is counted from the last real builder activity. Delivery is read back on every run into `notices` (`delivery` is Alido Mail's own wake state, `wake` its wake id). A Platform row that Alido Mail could not wake stays visible there as `failed`; the two-hour line to Vincent does not depend on it.

**Observation gap, changed rule.** The existing rule (one continuous gap over 20 minutes) resets on on-and-off loss. The changed rule trips on 20 unavailable minutes inside any hour or on the 3 newest readings all being unavailable (whatever their spacing), and its episode ends only after a full hour without tripping. A reading counts for the time until the next one, at most ten minutes, so the newest reading adds time only at the following run. The rule is always computed and written to `gap_rule`, and it is returned as `gapRule` in the job's output. It sends only when the loop switch `idle-observation-gap` is acting; until then the existing rule keeps sending exactly as before. Acting adds the changed rule to the existing one and never replaces it: a continuous gap over 20 minutes still alarms even when readings are too sparse for the changed rule, and while a changed-rule episode is open it carries the alarm so one loss is one incident. The mail says which rule tripped (`for 3 readings in a row`, `for 20 minutes within an hour` or `for over 20 minutes`), taken from the incident's stored evidence so the text does not change between retries. Before flipping the switch, attach the replay of the stored observations: `bun launcher/idle-queue.ts --replay <copy of idle-queue.sqlite>` prints, read-only, what each rule would have sent and what the idle rules would have done. Run it on a copy, never on the live file. The stored observations are private operational data and stay out of Git; the tests replay a fictional timeline of the same shape.

**Undo.** A signed revert of the source. The added tables (`records`, `notices`, `gap_rule`) are additive and ignored by the earlier source; keep them. Queued intake wakes named `intake:idle-repeat:*` are ordinary owner wakes; one still queued at the time of a revert is no longer withdrawn and is dispatched by the tick as an ordinary intake.

Pending incidents retain their original evidence and retry delivery even after work resumes. The notification describes the past incident and asks Coordinator to verify permanent product supply. When recovering a missed owner-reported incident during installation, retain the original report and real queue/custody/usage readback as incident provenance, separately from automatic observations. Never manufacture a current idle observation or change controller custody to rehearse an alarm.

After the product-only intake policy is installed, Coordinator can load a separate `com.agent-factory.product-top-up` job for `bun scripts/product-top-up.ts` every 1200 seconds with absolute paths and the existing private directory. This invokes the existing supply/backoff/custody lease and Product owner dispatch; the ordinary tick applies validated results and normal builder admission. It refuses pause, missing/stale usage and 90%, permits only high-benefit work in the 70–90% window, and changes no capacity or spending limit. No review/acceptance tickets are supplied by the installed product-only policy. Installation is distinct from source implementation: lint/bootstrap and read back the loaded interval and one actual run. Existing watchdog silence was structural: it required two hours idle, free capacity and an unpaused launcher, had no recovery message, and no independent watchdog launchd job existed. Qualification alerts ran inside tick at two hours and covered primary providers only. A stopped or paused tick could remove the observer itself. The new process continues to collect even when the controller cannot open or write its DB. Errors in the independent process remain in its own launchd error log; unavailable mail preserves durable pending notifications for retry.

AWS expiry uses only the existing non-secret original sign-in provenance file `release-auth-session.json`, never SSO tokens or AWS calls. Billing uses the existing cached `release-billing.json` import plus current read-only wallet stops/commitments. Holds use fresh read-only GitHub QA_HOLD and release-board label readback under the existing supported protocol. Missing, malformed or stale evidence remains actionable unknown. The independent watcher observes per-effort qualifications and suppresses a warning only with matching original qualification identity, actual current native model/effort and fresh process identity; a queued wake cannot supply this proof.

Bridge IDs are stable per condition, incident and destination. State is persisted before insertion. A successful insert means queued only. Vincent delivery needs the bridge's `telegram_messages` receipt; Coordinator delivery needs its recorded native wake. Notification retries reuse the same mail ID after crashes. Separate receipts prevent one destination hiding the other. Recovery requires newer positive evidence and two-hour opening/recovery rate limits remain in the evaluator.

After installation, `bun scripts/factory-health-watch.ts --rehearse YYYY-MM-DD` exercises a synthetic disk incident in memory and inserts exactly one clearly labelled test through the actual bridge, solely to Vincent. Its fixed date ID makes retries idempotent. Run again only to read delivery; no other condition or Coordinator is sent by the rehearsal. Preserve the returned ID and actual Telegram receipt privately. This does not alter controller evidence or manufacture qualification. Full six-condition source tests and real monitoring operation are separate from the single authorized Telegram test.
